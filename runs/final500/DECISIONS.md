# Decisions the spec did not settle (final 500-question study)

Rule used: pick the option that keeps the methodology hardest to question. Newest last.

## 13 Nov 2026

1. **Flex tier instead of the Batch API for build calls.**
   The spec asks for the OpenAI Batch API for offline build calls, transport only. The Batch API needs every request written out before any answer comes back. That works only for single independent calls. HippoRAG runs NER and then triple extraction on each chunk's NER output, RAPTOR summarises clusters built from the level below, and the graph build feeds extractions into entity resolution. Batching those would mean several record-and-replay rounds and new code in the build path. OpenAI's flex tier bills at the same rate as the Batch API (50% of list) but answers each request synchronously, so the build code runs unchanged. The only difference is one `service_tier: "flex"` field in each build Responses request body, added at the HTTP layer (`cost.py`, env `RECRAG_BUILD_SERVICE_TIER=flex`). Prompts, model, reasoning effort, settings, cache keys and index keys are unchanged. Tested 13 Nov: gpt-6-luna accepts flex and reports `service_tier: flex`. Sync, threaded and async build calls are all sent at flex, and question-time calls stay at the default tier. A flex request the API cannot serve right now (HTTP 429, not processed) is retried with backoff up to 5 times, then sent once at the default tier. Every attempt is logged as a failed call in the build cost.
2. **Answer runs stay at the default tier.** The spec limits the cheaper transport to offline builds, so question-time calls (retrieval agents, answers, closed-book) are not changed.
3. **HippoRAG build calls are now metered.** HippoRAG makes its OpenIE calls from worker threads, which do not inherit context variables, so its build calls were never metered (or sent at flex). `cost.indexing()` now also sets a process-wide build meter that calls from threads fall back to. Only metering and the tier change; HippoRAG's requests are unchanged.
4. **Natural Questions records are read from one saved file.** HippoRAG's separate environment cannot import the `datasets` package (its `pyarrow` is too old). Rows 0-499 were processed once by the existing `dataset._natural_questions_record` and saved to `natural_questions/records.json` (sha256 `476e4083…`). Every method reads that file (`RECRAG_NQ_RECORDS`), so all four see byte-identical records.
5. **HippoRAG's text splitter version differs (already true before this study).** HippoRAG's environment pins llama-index 0.11.23 and the main environment uses 0.14.25. On the NQ shared corpus, HippoRAG gets 21,553 chunks and the other methods 21,554. Every earlier HippoRAG run had the same difference. It is a property of the pinned upstream install, so it is reported, not changed.
6. **New MultiHop-RAG questions.** "Never used" was checked by scanning every .json, .jsonl, .md and .log file under `runs/` for MultiHop-RAG question ids, not only run outputs, and the held-out 400 were added to that list. 491 ids were excluded. 25 per type were drawn with seed 20261113 (`scripts/select_questions.py`, output `questions.json`).
7. **HotpotQA rows** come from the Hugging Face `hotpotqa/hotpot_qa` distractor validation split (7,405 rows). The 500 picked rows are saved as-is (`hotpotqa/questions_rows.json`), with the dataset fingerprint and file hash in `questions.json`, and read through `RECRAG_HOTPOTQA_ROWS`. The corpus is every paragraph of those 500 questions (4,860 distinct paragraphs, 5,122 chunks).
8. **Index builds use no study question.** `scripts/build.py` builds each HotpotQA and NQ index with the benchmark's own warm-up question, which is outside every question set and unscored, as at the start of every benchmark run. The answer runs then find the index already built.
9. **NQ graph build reuses the NQ 100 pilot's extractions** by copying the pilot's construction-cache rows into the new database's cache. Each cache key hashes the construction identity and the full extraction prompt, which includes the exact chunk text, so only byte-identical requests can hit. This is the spec's `build_reuse` rule.
10. **specguard.** It reported `ok` for reasoning effort and embedding model. The answer model (`[llm] model = "gpt-6-luna"`) was checked by eye. The other spec keys (counts, datasets, judging) are run choices that no config file holds; they are set in the launch scripts and checked by eye against `SPEC.md`.
11. **Build restarts.** Build calls are not retried, so one transient server error (HTTP 520, connection reset or a timeout) stopped a build. `scripts/build.py` restarts a failed build up to 20 times from its caches: graph extractions, HippoRAG replies and RAPTOR checkpoints are cached per call. Restart errors are kept in each `build/build_errors.log`. Spend metered by a process that was stopped and relaunched by hand is lost from `build_cost.json`. Cache sizes at the 10:42 UTC relaunch are in `cache_rows_at_restart.json`, so that unmetered part can be estimated: calls in the cache minus calls metered.
12. **Flex timeout.** Flex requests can wait longer than the 120 s config timeout, and several builds stopped on timeouts. A flex build request now gets 900 s (`cost.FLEX_TIMEOUT`). This is a transport setting only, and question-time calls keep the config timeout.
13. **HippoRAG OpenIE concurrency** was raised from 8 to 64 workers (`RECRAG_HIPPORAG_OPENIE_WORKERS`) because Natural Questions alone would have taken about 20 hours at 8. Each chunk's calls are independent, so the requests are unchanged.
14. **HippoRAG wrong-shape replies.** HippoRAG caches each OpenIE reply before parsing it. A reply like `{"entities": [...]}` instead of `{"named_entities": [...]}` is rejected and replayed from the cache on every restart: 7 on HotpotQA and 646 on Natural Questions. On restart, `build.py` deletes cached replies that have neither `named_entities` nor `triples`, so the model is asked again, the same as retrying that one call. Every dropped row is logged in `build/purged_cache_rows.json`, and HippoRAG's prompts and parser are unchanged.
15. **RAPTOR on Natural Questions** failed once in the clustering step: sklearn GaussianMixture reported an ill-defined covariance. RAPTOR's UMAP step has no fixed seed, so the run was retried once with no change, as allowed. If it fails again, the decision will be recorded here.
16. **Claims stage.** 124 files, one Haiku subagent each, launched by 3 coordinator subagents that only launch, check and relaunch once. 116 passed at first or on the one relaunch.
    - 7 Natural Questions questions have a single long-answer paragraph that the judge returned as several fact lists, one per sentence inside the paragraph. `evals/haiku_fact_judge.merged_single_passage` joins those lists in order when the question has exactly one gold passage. Nothing is added or dropped, and it is applied the same way to every question.
    - One HotpotQA file (089) failed twice by merging sentences. A third fresh subagent passed. The failed reply is kept in `claims/failed/`.
    - Two files passed the check but their own subagents flagged them: 073 said it added details the source does not state, and 112 said its file changed mid-edit. Both were redone by fresh subagents, with the originals kept in `claims/failed/`.
    - Result: 1,233 questions (MultiHop-RAG 375, HotpotQA 500, Natural Questions 358) and 22,190 frozen facts.
17. **Answered right is judged fresh.** All answers that are not exact matches, including the 400 MultiHop-RAG answers reused from the held-out run, go to a new Haiku answer judge in `judge/answers`. No earlier answer verdict is reused.
18. **Closed-book baseline** reads the questions straight from the frozen sets with the same prompts and scorer as `evals/closed_book.py`. Each question gets 2 attempts, and all 4,500 answered, with 0 failed.
19. **NQ graph build concurrency.** At 20 concurrent extractions, flex latency put the Natural Questions graph build at about 1,700 chunks an hour, so it would have taken another 8 hours. It was restarted at 12:50 UTC with `RECRAG_CONFIG=runs/final500/config.build.toml`, a copy of `config.toml` that differs only in `extraction_concurrency = 80`. Concurrency is part of neither the construction cache identity nor the graph index key, so the extractions are the same requests. Answer runs use `config.toml`.
20. **Questions seen before.** 27 of the 500 HotpotQA ids appear in files from older HotpotQA runs. No Natural Questions row from 100 to 499 appears anywhere earlier. For the Agentic GraphRAG "never used in tuning" results, the set excludes:
    - all 400 held-out MultiHop-RAG questions, because the 2 Nov results on them were analysed while the method was changed;
    - Natural Questions rows 0-99, the pilot, which the 10 Nov version also ran on;
    - those 27 HotpotQA questions.
    What remains is the 100 new MultiHop-RAG questions, 473 HotpotQA and 400 Natural Questions. The 38 swinging comparison questions are listed by id in `tuning_questions.json`.
21. **Map-valued graph property.** One cached Natural Questions graph extraction gave `"coordinates": {"latitude": ..., "longitude": ...}` as a node property. Neo4j stores only primitive values, so writing the graph failed on every restart. That one cached reply was deleted so the model is asked again, the same as retrying one call. `build.py` now does this on restart, and every deleted row is logged in `build/purged_construction_rows*.json`. The graph build code and prompts are unchanged.
22. **RAPTOR build speed.** RAPTOR wrote its summaries one at a time and rewrote its whole checkpoint after every step, twice. On Natural Questions the checkpoint is 684 MB, which gave about 220 summaries an hour, or about 30 more hours for layer 1 alone. `raptor_retrieval.py` now has two options, both off by default:
    - `RECRAG_RAPTOR_WORKERS` sends a layer's missing summary requests in parallel. The prompt is unchanged, and results are used in cluster order exactly where the one-by-one loop would make them. Summaries within a layer do not depend on each other.
    - `RECRAG_RAPTOR_CHECKPOINT_EVERY` saves the checkpoint every N steps instead of every step.
    The Natural Questions RAPTOR build was resumed from its checkpoint at 16:45 UTC with 48 workers and a save every 500 steps. The output is the same as the sequential loop would produce, apart from the sampling noise any regenerated call has.
23. **App restart, about 17:00 UTC 13 Nov.** A restart of the agent app killed every job started from its shell: the Natural Questions graph and RAPTOR builds, and the Natural Questions Normal RAG and HippoRAG answer runs, which had 0 rows saved. All four were relaunched at 17:31 UTC in their own sessions (`scripts/detach`). Builds resumed from their caches and checkpoints. RAPTOR summaries made in parallel before the restart but not yet checkpointed were lost and are made again; that is paid twice and not in the metered spend.
24. **Natural Questions moved to the Instabox VM (13 Nov, about 19:00 UTC).** On 13 Nov at 22:22 local time, the 12-shard Natural Questions answer launch plus the two builds and Neo4j used about 70 GB and froze the Mac. The rest of the Natural Questions work runs on the VM `omarchy-mpv0`: 4 vCPU, 8 GB RAM, repo at `/data/workspace/RecRAG`.
    - The environment is the same: `.venv` and `.venv-hipporag` were installed from the Mac's exact package lists, with CPU-only torch 2.5.1 in `.venv-hipporag`.
    - Neo4j runs in Docker (`neo4j:2026.09.0-enterprise` with APOC) with a smaller heap: 1 GB heap and 512 MB page cache.
    - Code, caches, indexes and question files were copied from the Mac.
    - `scripts/vm_queue.sh` runs one heavy process at a time: the graph build, the RAPTOR build, then answers (rag with 2 shards, raptor 2, graphrag 3, hipporag 1, one repeat at a time). It skips finished steps when restarted.
    - Fewer parallel shards change only wall time, not requests.
25. **Graph build memory on the VM.** neo4j-graphrag's `SimpleKGPipeline` runs all 21,554 chunks as one batch. It keeps every chunk embedding and every extracted graph in memory, and its in-memory result store keeps another copy of each step's output. It reached about 6-7 GB RSS in 5 minutes on an 8 GB VM with 4 GB swap. Splitting the build into batches would change how chunks are linked and merged, so it was not done. Instead a 6 GB swapfile was added on the VM root disk (`/swapfile2`, 10 GB swap in total), and the same build was rerun unchanged. Memory is logged every minute in `jobs/vm_mem.log` on the VM.
26. **NQ graph build finished on the VM** (13 Nov, 19:18 to 19:32 VM clock, 795 s). Every extraction came from the cache, so it made no API calls. With the extra swap it peaked at about 6.5 GB RSS plus 4-5 GB swapped, and the VM stayed responsive.
27. **RAPTOR parallel summaries are retried per call.** On the VM, the NQ RAPTOR build failed 18 times. Under 16 parallel requests, connections dropped (SSL EOF, server disconnects) and flex capacity ran out (HTTP 429). One failed summary aborted the whole layer's parallel batch, and the summaries already made in it were lost: 4,859 metered calls, $0.36, with nothing checkpointed. `raptor_retrieval.summarize_retrying` now asks a failed summary again, up to 3 tries, and a cluster that still fails is left to the one-by-one loop as before. The prompt and the order are unchanged. Workers went from 16 to 8. The build was restarted from its checkpoint at 21:20 VM clock.
28. **RAPTOR parallel summaries are saved as they arrive (14 Nov, code synced 23:15 UTC 13 Nov).** The parallel step kept all of a layer's new summaries in memory until every request had returned; only then did the loop use them and write the checkpoint. On NQ layer 1 that is 6,652 summaries, about 2+ hours on flex, so a stop before the end (the VM's 8-hour limit, a crash) loses all of them. Now the loop takes each result in cluster order as soon as it arrives, so the save every 500 summaries happens during the layer. On error the remaining requests are cancelled, so a restart inside build.py does not run two batches at once. Speed and safety only: same prompt, same order, same clusters. Checked on a 400-document fake corpus with fixed clusters and 5% random call failures: 1 worker, 1 worker again, and 4 workers saving every 7 gave identical trees. The build running at the time (started 21:18 UTC) still uses the old code; the new code is used only if it restarts.
